From card photo to NID fields

What happens to an NID image in our pipeline. First, the preprocessing recipes that clean the ink before OCR. Then each step inside Tesseract, from a greyscale image to the text of each field.

  • Tesseract 5.5.3 · Leptonica 1.87
  • Engine --oem 1 (LSTM only)
  • Page default --psm 6
  • Models ben + eng

OverviewThe whole pipeline in one picture

Three owners touch the image. Our code prepares it. Tesseract binarizes it, finds the lines and reads them. Then our code reads each NID row again and parses the fields. The green dashed path is the one people miss: the black-and-white image is only used to find the text. The LSTM reads each line from the non-binary image.

Part 1 · PreprocessingFour recipes, one final image

Before OCR, inspect_preprocessing() runs one recipe on the image. Each step is saved as a numbered PNG in the working folder. The recipe hands one file, 99-final-ocr.png, to Tesseract. On an NID card the enemy is colour: a yellow-orange emblem and a guilloche watermark sit behind black text. Every recipe starts by dropping the red and blue channels for that reason.

Step reference

The constants below are the values in the code today. Change them and the output changes.

  1. 00-input.png

    Input image

    ImageOps.exif_transpose fixes phone orientation, then the image is converted to RGB. The DPI metadata is kept and written into every later PNG.

    Why: a sideways EXIF flag would reach Tesseract as rotated text. Losing DPI makes Tesseract guess the text size.

  2. 01-green-channel.png

    Green channel

    image.getchannel("G"). Keep one of three channels and drop the other two.

    Why: yellow and orange are bright in green, so the emblem fades toward the card background. Black text is dark in every channel, so it stays dark.

  3. 02-background-estimate.png

    Background estimate

    Gaussian blur. Radius max(9, min(w,h) // 28), kernel max(17, radius | 1), and cv2 derives sigma from the kernel. Without OpenCV it falls back to PIL GaussianBlur(radius).

    Why: the blur is wide enough to wipe out text strokes. What is left is paper tone, emblem, shadow and glare, which are the things to remove.

  4. 03-background-normalized.png

    Background normalized

    green / max(bg, 1) × p88(bg), clipped to 0–255. Dividing flattens slow changes in light. Multiplying by the 88th percentile of the background keeps the paper near its original brightness.

    Why: a shadow darkens text and paper by the same factor, and division cancels it. Subtraction can't do that.

  5. 04-controlled-contrast.png

    Controlled contrast

    ImageOps.autocontrast(cutoff=0.5). Clip 0.5% of pixels at each end of the histogram and stretch the rest to 0–255. v1 clips 1%.

    Why: after normalization, gentler clipping is enough. It keeps thin Bengali strokes (matra, vowel signs) that 1% clipping can erase. Current best final image.

  6. 05-ink-mask.png

    Ink mask (diagnostic)

    A pixel is ink if it is ≤ the 38th percentile, with that cutoff clamped to 20–245. Then a morphological open with a 2×2 kernel removes single-pixel specks.

    Why: it shows what counts as ink. It assumes about 38% of the image is ink or dark, which is a guess tuned for card crops, so treat it as a check and not as ground truth.

  7. 06-nid-ink-v2-masked.png

    Masked text-ink image

    Outside the mask: px × 1.06 + 6, which lightens. Inside the mask: px × 0.78, which darkens. The result stays greyscale.

    Why: stronger ink and paper separation without a hard binary, because the LSTM reads grey better than black and white. It is the final image only for nid_ink_v2.

  8. 99-final-ocr.png

    Final OCR image

    A copy of the recipe's chosen output: 00 (off), 02 (v1), 04 (v2 contrast) or 06 (v2 masked). It is saved with the original DPI.

    Why a separate file: Tesseract always reads one predictable path, so recipes can be swapped without touching the engine code.

Part 2 · TesseractInside one Tesseract run

inspect_steps() in engines/tesseract_steps.py calls Tesseract once through the C API. It saves every intermediate result so the dashboard can show it. Tesseract works in two phases. Layout finds where the text is without reading anything. Recognition reads one line at a time.

The one rule to remember: a row that the layout step (4–8) drops never reaches the LSTM, and model training can't bring it back. Fix missing rows with preprocessing, crop, rotation or PSM. Train only for misread characters.

Thresholding methods

Set thresholding_method in the dashboard. The window sizes depend on DPI. When the DPI is missing or outside 70–2400, Tesseract uses 70, so the windows get very small. normalize_threshold() checks each value against these limits.

With manual, the LSTM reads the binary image too. That is the only method where a bad threshold also hurts recognition. With the other three, a bad threshold only hurts layout.

Layout hierarchy and PSM

Layout builds a tree: page → block → paragraph → line → word → symbol. PSM (page segmentation mode) sets how much of that tree Tesseract searches for and how much it assumes. Only PSM 1, 2, 3, 4, 11 and 12 run automatic column finding, so only those modes write Tesseract's own PageSegInput / NoLines / NoImages debug images.

PSMAssumesWhere we use it
0Orientation and script detection onlyAuto rotation. Rotate if confidence ≥ 2.0, otherwise try 0/90/180/270.
3Fully automatic layoutSweep candidate. Can split the photo and the text into odd blocks.

6One uniform blockPage default. The whole card is one block, and lines are still found.

LSTM line recognition

With --oem 1, each line crop is scaled to a fixed height and read as a sequence. The model never cuts the line into characters. At every thin vertical slice it outputs a probability for each character in the model's character set (the unicharset), plus a blank. CTC decoding then merges repeated characters and drops the blanks. This is why joined Bengali letters, where the matra links a whole word into one blob, are read correctly.

Time step t1t2t3t4t5t6t7t8t9t10t11 Best output RR∅AA∅H∅IIM Collapsed RAHIM

Green = kept. Grey = a repeat that gets merged. Dashed ∅ = blank, which gets dropped.

A bidirectional LSTM reads the line forwards and backwards, so each character is judged with both neighbours in view. The beam search keeps the top few candidate readings and scores them with the word dictionaries (DAWGs) inside the .traineddata file. That helps with ordinary words and can hurt names and ID numbers, which is why the NID number row uses a digit-only whitelist. With -l ben+eng, both models run, and the better reading wins per word. Confidence is 0–100 per word. Treat it as a signal, not a guarantee.

NID field re-read

A single page pass mixes scripts and sometimes drops a row. refine_nid_fields() uses what the page pass found, then reads each NID row again on its own crop with one language.
