Why vision LLMs read NID cards better than Tesseract

In the dashboard, Gemini and LM Studio (Qwen2.5-VL) usually return cleaner NID fields than Tesseract, EasyOCR or PaddleOCR. The LLMs don't have sharper eyes. They are doing a different job: one model looks at the whole card and writes the answer, while the OCR engines pass the image through a chain of separate steps, and each step can lose something.

  • LLM engines: gemini_vision, lmstudio_vision
  • OCR pipelines: tesseract, easyocr, paddleocr

Short answerFive reasons, most important first

  • One step instead of a chainOCR engines binarize, detect, cut, read and parse. Each step multiplies the chance of an error. The LLM does all of it in a single model.→ error chain
  • It sees the whole cardTesseract reads a thin strip, one line at a time. The LLM sees every line, the layout and the prompt together, so a blurred letter can be worked out from its surroundings.→ what the reader sees
  • It answers the actual questionWe ask the LLM for fields and it returns JSON. The OCR engines return plain text, and our regex parser has to find the fields in it. A misread label loses the field.→ text vs fields
  • It is roughly 550–7,000× biggerQwen2.5-VL on disk is 6.0 GB. Tesseract's Bengali model is 0.86 MB (fast) or 11 MB (best). That size holds knowledge of Bengali names, dates and ID cards.→ model size
  • Our comparison is partly unfairThe PaddleOCR adapter always loads the English model, EasyOCR uses greedy decoding, and the parser is basic. The OCR engines start behind.→ our adapters

Steps · LLM enginesWhat Gemini and LM Studio actually do

Both adapters send the same prompt (VISION_PROMPT in lmstudio_vision.py) with one image in a single request. Steps 01–04 and 06–08 are our code. Step 05, shaded, happens inside the model: we can't watch it, so it describes how vision-language models work in general.

  1. Prepare the input image

    Same crop, filter and preview rotation as every other engine.

    server.py · prepare_ocr_input()

  2. Skip the orientation search

    rotation="auto" becomes 0°. No OSD pass and no four-way retry. The model reads the card as given.

    run_lmstudio_vision() · run_gemini_vision()

  3. Encode the image

    Raw file bytes → base64, sent as PNG or JPEG. The model gets the image at full colour, with no binarization.

    _image_base64() · _image_data_url()

  4. Send one request: image + prompt

    The prompt names the 10 keys and the rules: keep Bangla in Bangla script, digits only for the NID, null when a field isn't visible, front or back side. Settings: temperature 0.
    Gemini: responseMimeType: application/json, 4096 output tokens, retries on 429/5xx after 1 s and 2 s.
    LM Studio: OpenAI-style chat API, 900 max tokens, reasoning_effort: none so thinking models don't spend the whole budget reasoning.

    _generate_content() · _chat_completion()

  5. Inside the model

    See, then write the answer

    (a) The image is cut into small patches, and a vision encoder turns each patch into a token. (b) Those image tokens and the prompt tokens form one sequence. (c) The decoder writes the JSON one token at a time. Each token can use every image patch, the whole prompt, and all the JSON written so far. So when it writes the English name, it can use the Bengali name above it, the card's layout, and what it knows about Bangladeshi names.

    not visible to us · general VLM design

  6. Extract JSON from the reply

    Strip ``` fences and take the text from the first { to the last }. If the JSON was cut off, Gemini's adapter still recovers the complete "key": "value" pairs one at a time.

    _parse_field_json() · _salvage_field_json()

  7. Normalize the fields

    Keep the 10 known keys, trim whitespace, and turn empty strings into null.

    normalize_fields()

  8. Map to NIDData without the parser

    Every non-empty value gets confidence 0.80 and needs_review=True. No regex, no label matching, no word boxes.

    nid_data_from_vision_fields()

Then NIDParser does the last step for all three:

  1. NID number

    Look for ID/NID NO followed by ≥ 8 digits. Otherwise take any run of 10, 13 or 17 digits. Bengali digits are converted to 0–9.

    find_nid_number()

  2. Date of birth

    Prefer a line containing birth or জন্ম. Try "01 Jan 1990", then ISO, then D/M/Y. The date must be a real calendar date.

    find_date_of_birth()

  3. Labeled names and addresses

    Find the label (নাম, Name, পিতা, মাতা, ঠিকানা…) at the start of a line or before a colon. The value is the rest of that line, or the next line. At least 60% of its letters must be in the expected script. Fixed confidence 0.55.

    find_labeled_value()

Why · 1Errors multiply along a chain

If a field has to survive five separate steps, it arrives only if every step gets it right. Suppose each step is right 95% of the time. After five steps, only 77% of fields survive. The LLM still makes mistakes, but it has fewer separate places to make them.

Why · 2What each reader sees when it reads one word

Tesseract's LSTM reads the name রহিম from one line crop, scaled to a fixed height. Its bidirectional memory covers that line and nothing else. The LLM reads the same word with the whole card in view, plus the prompt, so it knows this is a Bangladeshi NID and this row is a name.

Why · 3OCR returns text, but we need fields

A perfect OCR read can still produce a missing field. The parser finds values by their labels, so the label has to be read correctly too. The LLM is asked for the field directly and never has to spell the label.

Tesseract → NIDParser
card rowনাম: মোঃ রহিম উদ্দিন

name_banglanull

The name itself was read correctly. The field was lost because one letter of the label was misread. (The fields strategy knows লাম as an alias, but the base parser doesn't.)

Vision LLM
card rowনাম: মোঃ রহিম উদ্দিন

reasoningfirst Bengali row after the header = holder's name
name_banglaমোঃ রহিম উদ্দিন

It knows where a name sits on an NID card, so the label is just a hint.

The same gap shows up elsewhere. A line box that merges two rows gives the parser one line with two labels. A value that wraps to the next line only works if that line has no digit and doesn't start with a label word. A date printed in an unexpected format fails the regex. The LLM handles all of these because the prompt tells it what each field means.

Gemini 3.6 Flash isn't on the chart: it runs in Google's cloud and its size isn't published. The Qwen size is the 4-bit Q4_K_M weights (4,683 MB) plus the f16 vision projector (1,354 MB).

Size is not skill, but it sets a ceiling. An 0.86 MB LSTM can store Bengali letter shapes. A 6 GB model trained on huge amounts of web images and text can also store which names are common, how dates are written, and what an ID card looks like. That extra knowledge is what fills gaps when pixels are unclear. It is also what makes hallucination possible (see below).

CautionWhy "seems" is the right word

No labeled benchmark has been run yet. benchmark/reports/ is empty and benchmark/datasets/ has no annotated cards. "The LLM is better" is an impression from the dashboard, not a measured result.

Several things make an LLM answer look better than it is:

  • Wrong answers look fluent. When the LLM can't read a character, it writes a plausible one: a common spelling of a name, or a digit that fits the pattern. Tesseract's mistakes look like garbage (রহি।ম), so they are easy to spot. The LLM's look correct.
  • The confidence is made up. Every non-empty LLM field gets 0.80, whether it's right or not. There is no per-character probability to check against.
  • No boxes, so no audit. The output has no coordinates, so you can't overlay the answer on the image to check where each value came from.
  • The prompt allows rewriting. "Return only digits" and "keep values concise" invite normalization. A field can come back reformatted rather than as printed, which is fine to read but fails an exact-match check.
  • Easy cards dominate the impression. On a clean card every engine does well. The ranking that matters is on glare, blur and small print, measured per field.

Treat LLM output as a strong second opinion, never as ground truth. Docs/tesseract_accuracy_speed_cost_plan.md sets the same rule for labeling.
